## 问题引出

在 [OJ](https://pry.jsu.edu.cn) 的测试过程中，有团队成员提出了这样一个问题：

> 一个学生若在考试前登录了网页端，那么考试开始后，他在考试端登录，他是不是还可以在网页端答题？

OJ 整个系统的设计参考了微服务思想，将业务水平分割，分为多个服务模块，部署在多台服务器中，对于权限的校验采用的是分散鉴权（去中心化），通过打包 `OJ-Authority-Filter` 模块，登录时生成带权限的 token，各服务器处理请求前都会解析 token 判断是否有权限调用接口。

但正因为 token 是无状态的，因此也导致了它最大的缺点：**不可控！**

这个问题看起来只是一个「多端登录」的业务细节，但往下追一层，它触碰的其实是 JWT 方案的根本矛盾：**我们选择 JWT 是为了不存状态，而"把某个已签发的凭证作废"这件事，天然需要状态。** 下面我把这个矛盾拆开，逐个场景讨论。

---

## 一、先说清楚：我们为什么选了 JWT

在讨论缺点之前，有必要先承认它在我们这个架构下确实带来的收益，否则后面的取舍会失去参照系。

**1. 无状态，天然适配去中心化鉴权。**
JWT 自身包含了身份验证所需要的全部信息，服务端不需要保存会话记录。这正是 `OJ-Authority-Filter` 能以一个 jar 包的形式嵌进每个服务的前提——判题服务、题库服务、考试服务各自独立校验签名即可，不需要回头找认证中心，也不需要一个共享的 Session 存储。服务扩容时不用考虑会话粘性（sticky session），这在水平切分的架构里价值很大。

**2. 传输方式带来的 CSRF 风险更低。**
如果客户端把 JWT 作为 Bearer Token 显式放进 HTTP `Authorization` 头，浏览器不会像对待 Cookie 那样自动把它附带到跨站请求上，因此可以规避传统的 CSRF 攻击路径。

这里要强调一句，很多文章会把这条写成「JWT 天生防 CSRF」，这是不准确的：**起作用的是凭据的传输方式，而不是 JWT 这种数据格式本身。** 如果你把 JWT 塞进 Cookie 并依赖浏览器自动携带，CSRF 风险和 SessionID 没有任何区别。

**3. 适合多端。**
OJ 至少有网页端和考试客户端两个入口。Session + Cookie 的方案在桌面客户端上会很别扭（Cookie 管理、跨域），而 JWT 只要客户端能存下来就能用，跨语言、跨平台。

**4. 单点登录友好。**
Session 方案做 SSO 要处理 Cookie 跨域和会话共享，JWT 保存在客户端，天然绕开了这些问题。

## 二、核心问题：注销、踢下线、改密之后，JWT 依然有效

这是 JWT 最广为人知的痛点，也是我们那个提问的本质。相关场景不止一个：

- 用户主动退出登录；
- 用户修改密码；
- 服务端修改了某个用户的权限或角色（比如把一个学生临时提升为助教，或者撤销）；
- 用户账号被封禁 / 删除；
- 用户被服务端强制注销；
- **用户在新设备登录，需要把旧设备踢下线**（我们的场景）。

在 Session 方案里这些都不是问题——服务端删掉对应的 Session 记录就完了。但 JWT 一旦签发出去，在过期之前它就是有效的，除非后端额外增加逻辑。

下面是几种主流解法，以及它们各自的代价。

### 方案 1：把有效 JWT 存进数据库（不推荐单独使用）

把签发出去的 JWT 存入数据库（更建议用 Redis 这类内存数据库），需要作废时直接删除。

代价很直白：**每次请求都要查一次 Redis，而且彻底违背了无状态原则。** 这时候 JWT 相比"随机字符串 + Redis"的传统 Token 已经没有优势了——你既付出了 JWT 的体积成本，又付出了 Session 的存储成本。

### 方案 2：黑名单机制（实用，但要注意粒度）

思路相反：不存有效的，只存被作废的。用 Redis 维护一个黑名单，要让某个 JWT 失效就把它的 `jti`（JWT ID）加进去，每次请求先判断是否在黑名单中。

比方案 1 好在两点：

- 黑名单是稀疏的，绝大多数用户从不主动登出，存储量远小于全量 token；
- **可以给黑名单记录设置 TTL，等于该 token 的剩余有效期。** token 自然过期后，黑名单记录也自动清理，集合不会无限膨胀。

```java
// 注销时：把 jti 拉黑，TTL = token 剩余生命周期
public void logout(String jti, Date expiration) {
    long ttl = expiration.getTime() - System.currentTimeMillis();
    if (ttl > 0) {
        redis.opsForValue().set("jwt:blacklist:" + jti, "1", ttl, TimeUnit.MILLISECONDS);
    }
}
```

它的局限在于**粒度太细**：黑名单作用于单个 token。如果要「让某个用户的所有 token 失效」（改密、封号、踢下线），你得先知道这个用户签发过哪些 token，又绕回了方案 1。所以实际项目里，黑名单通常和下面的方案 4 配合使用。

### 方案 3：为每个用户维护独立密钥（不推荐）

给每个用户创建专属签名密钥，想让某个用户的 JWT 全部失效，就换掉他的密钥。

听起来很优雅，但在我们这种分布式架构下危害更大：

- **密钥必须在所有服务间同步。** 签发新 JWT 时要把密钥推送到多台机器，或者存到数据库/外部服务里让大家来查——那和 Session 认证已经没有区别了；
- **粒度依然是"用户级全量作废"。** 用户同时在浏览器和手机端登录，从一处退出会导致所有端全部掉线，用户体验很差。

有一个变体倒是值得一提：**用「用户密码的哈希值」参与 JWT 签名**。这样密码一改，此前所有 token 的签名自动失效，不需要任何额外存储。它精准解决了"改密后 token 仍有效"这一个场景，但同样有全端掉线的副作用，且每次校验都要读取用户密码哈希。

### 方案 4：令牌版本号 / 会话标识（推荐）

这是我认为最适合 OJ 这类系统的方案，也是黑名单的一个"降维"版本。

核心思路：**不去追踪每一个 token，而是在 JWT 里放一个可比对的"世代标记"，服务端只维护这个标记的当前值。**

在 payload 中加入若干自定义 claim：

| claim | 含义                                       |
| ----- | ------------------------------------------ |
| `jti` | token 唯一 ID，用于精确拉黑                |
| `ver` | 用户凭证版本号。改密、封号、权限变更时递增 |
| `sid` | 会话 ID。每次登录生成一个新的              |
| `dev` | 客户端类型，如 `web` / `exam-client`       |

Redis 中只需要为每个用户维护一条极小的记录：

```
auth:user:{uid}  ->  { ver: 7, sid:web: "a1b2...", sid:exam-client: "c3d4..." }
```

`OJ-Authority-Filter` 的校验流程变成：

```java
public AuthResult verify(String token) {
    Claims claims = parseAndVerifySignature(token);   // 1. 验签 + 校验 exp/iss/aud

    Long uid = claims.get("uid", Long.class);
    UserAuthState state = authStateCache.get(uid);    // 2. 读取当前状态（带本地缓存）

    // 3. 版本号比对：改密 / 封号 / 权限变更后，旧 token 全部失效
    if (claims.get("ver", Integer.class) < state.getVer()) {
        return AuthResult.expired("credential_changed");
    }

    // 4. 会话比对：同类型客户端只保留最后一次登录，实现"踢下线"
    String dev = claims.get("dev", String.class);
    if (!Objects.equals(claims.get("sid"), state.getSid(dev))) {
        return AuthResult.expired("logged_in_elsewhere");
    }

    return AuthResult.ok(claims);
}
```

这套设计的好处：

- **作废操作是 O(1) 的**：改密就 `ver++`，踢下线就覆盖 `sid`，不需要遍历或追踪任何 token；
- **粒度可控**：`ver` 管用户级全量作废，`sid` 管单端作废，`jti` 黑名单管单 token 作废，三层各司其职；
- **存储量极小**：每个活跃用户一条几十字节的记录，可以直接设置 TTL 等于 refresh token 的生命周期。

**关于性能：** 会有人担心「每个请求都读 Redis，不就失去无状态的意义了吗」。这是个合理的质疑，但要注意两点。第一，我们读的是一条固定的小记录，不是变长的 token，可以在各服务本地加一层 Caffeine 缓存（TTL 几十秒到几分钟），并通过 Redis Pub/Sub 或消息队列在状态变更时广播失效，把 Redis 的 QPS 压到很低。第二，也是更重要的——**在"完全无状态"和"完全可控"之间，本来就不存在两全其美的点，我们能做的只是把滑块放在合适的位置。** 只要你的业务需要"立即踢下线"，就必须付出某种形式的状态成本，区别只在于这个状态是一整份会话，还是一个版本号。

### 方案 5：缩短有效期并频繁轮换

最简单的一种：把 token 有效期设得很短（比如 15 分钟），过期后重新走登录。作废动作的最大延迟就是这个有效期。

代价是用户登录状态无法持久保持，需要频繁重新登录。单独用不现实，但它是下一节 refresh token 方案的基础。

## 三、续签问题：过期了怎么办

JWT 有效期建议设得短，那过期之后如何避免用户频繁重新登录？

Session 方案的做法很自然：有效期 30 分钟，30 分钟内有访问就顺延 30 分钟。JWT 这边有几种做法：

**1. 快过期时下发新 token（不推荐）**
服务端每次校验时，发现 token 快过期就重新签发一个塞进响应头，客户端比对新旧 token 并更新本地存储。问题是只在临近过期时才更新，客户端要一直做这个比对逻辑，不够友好。

**2. 每次请求都返回新 token（不推荐）**
思路简单，但签发开销大，尤其在服务端还要维护 token 状态的情况下。

**3. 有效期设到半夜（不推荐）**
折中方案，保证大部分用户白天不掉线。适用于对安全性要求不高的系统——**但 OJ 涉及考试场景，显然不属于这一类。**

**4. 短期 access token + 长期 refresh token（推荐）**

签发两个凭证：

- **access token**：生命周期短（15~30 分钟），随每个业务请求携带，各服务本地验签即可；
- **refresh token**：生命周期长（几天），**只用于换取新的 access token**，只发往认证服务的一个专用端点。

关键在于：**refresh token 是有状态、可撤销的。** 它存在 Redis 里，注销、改密、封号时直接删除。这样整套方案的性质就变了：

> 业务请求走纯无状态校验（可能带一层短 TTL 的状态检查），而"撤销"这个动作在 refresh 时刻强制生效。**作废的最坏延迟 = access token 的有效期。**

对绝大多数场景，"最多 15 分钟后彻底失效"是完全可以接受的。而对于考试这种强实时的场景，再叠加上一节的 `ver`/`sid` 校验做即时拦截。

需要注意的坑：

- **需要客户端配合**，最好在客户端设置定时器，在 access token 快过期时提前刷新，避免出现短暂不可用的窗口；
- **refresh token 是攻击者的首要目标**，它权限高、存活久，不要因为"使用频率低"就觉得不容易泄露；
- **必须做刷新令牌轮换（rotation）**：每次刷新都作废旧的 refresh token 并下发新的，同时检测旧令牌重放——如果一个已被使用过的 refresh token 再次出现，说明大概率发生了泄露，应立即作废该用户的整条刷新链；
- refresh token 应绑定客户端、授权范围和资源服务器，并设置闲置过期时间。

## 四、回到最初的问题：网页端和考试端

有了上面的工具箱，回头看那个提问。它其实不是一个问题，而是**两个被混在一起的问题**，分开处理才干净。

### 问题 A：身份层面 —— 同一个账号能不能同时有两个活跃会话？

这是纯粹的鉴权问题，用上面的 `sid` 机制解决。这里有两种策略可选：

**策略 1：全局单会话。** Redis 里每个用户只保留一个 `sid`，任何端登录都会覆盖它，旧端的下一个请求就会被判为 `logged_in_elsewhere`。实现最简单，但学生考完试想回网页端看题解，还得重新登录一次，体验有折损。

**策略 2：按端分会话。** 即前面示例代码的做法，`sid` 按 `dev` 分别存储。网页端和考试端各自维护一个会话，互不影响；同一端重复登录才会互相顶掉（防止账号共享）。

我更倾向策略 2——**因为"网页端能不能答题"根本不是身份问题，把它塞进鉴权层是错配。**

### 问题 B：业务层面 —— 考试期间，答题入口应该在哪里？

这才是团队成员真正担心的：学生用考试端进入考试（可能带着防作弊、锁屏、全屏监控等约束），同时用网页端绕过这些约束提交答案。

**这个约束应该由考试服务来表达，而不是由 token 来表达。** 理由很简单：token 是身份凭证，它回答的是"你是谁、你能调用哪些接口"；而"当前这场考试的答案只接受来自考试端的提交"是一条业务规则，它依赖考试状态、时间窗口、考场配置，这些信息不该也不可能塞进一个签发时就固定下来的 token。

具体做法：

1. 学生从考试端进入考试时，考试服务写入一条考试会话记录：`exam:session:{examId}:{uid} -> { sid, dev, startAt }`；
2. 提交/保存答案的接口，除了常规鉴权外，**额外校验请求携带的 `sid` 与 `dev` 是否等于该场考试记录中的值**；
3. 不匹配则返回一个明确的业务错误（如 `409 EXAM_SESSION_MISMATCH`，提示"本场考试已在考试客户端进行中"），而不是 401。

这样网页端在考试期间依然能登录、能查看公告和历史提交——**它被限制的是"答题"这一个动作，而不是整个身份。** 这就是"权限降级"而非"全量踢下线"，用户体验和安全约束都能兼顾。

一句话总结这一节的思路：**鉴权层负责回答"这个身份还有效吗"，业务层负责回答"这个操作现在允许吗"。不要把所有约束都往 JWT 里塞。**

## 五、其他容易被忽略的问题

### 1. JWT 体积太大

JWT 由 Header、Payload、Signature 三部分组成，还要经过 Base64Url 编码，体积通常在几百字节到 1~2 KB。**而它会附加在每一个请求上**，在高频接口（比如判题状态轮询）上，这个开销会被放大。

缓解办法：

- **精简 payload**，只保留必要的用户标识和权限信息。特别提醒：如果权限列表很长（比如把每个接口的权限码都塞进去），应该改成存角色 ID，由服务端映射；
- 传输前用 GZIP 等算法压缩；
- 在某些场景下，传统 Token（随机 ID + Redis 查询）反而更合适。

### 2. Payload 不是加密的

`Base64Url` 是编码，不是加密。**任何拿到 token 的人都能直接解出 payload 内容。** 绝不要在里面放密码、手机号、身份证号等敏感信息。确实需要加密载荷时，用 JWE。

对我们的场景，还有一个具体的坑：**不要把"这道题的正确答案"或任何考试敏感信息放进 token。**

### 3. 算法混淆与 `alg=none`

这是 JWT 最经典的攻击面（RFC 8725 专门列出）：攻击者把 header 里的 `alg` 改成 `none`，某些库会信任这个值，跳过签名校验直接"验证通过"。

**防御方式只有一条：服务端硬编码期望的算法，绝不从 token 中读取。**

```java
Jwts.parser()
    .verifyWith(publicKey)
    .sig().add(Jwts.SIG.ES256).and()   // 显式指定算法，拒绝其他一切
    .requireIssuer("oj-auth")
    .requireAudience("oj-judge")
    .build()
    .parseSignedClaims(token);
```

### 4. 分布式下的密钥选择：别用 HS256

这一点对我们的架构尤其重要。`OJ-Authority-Filter` 被打包进每一个服务，如果使用 HS256 这类对称算法，**意味着每个服务都持有签名密钥——任何一个服务被攻破，攻击者就能伪造任意用户、任意权限的 token。**

正确做法是使用非对称算法（RS256 / ES256）：

- **只有认证服务持有私钥**，负责签发；
- 其他服务只持有公钥，仅能校验，无法伪造；
- 公钥通过 JWKS 端点分发，配合缓存和密钥轮换。

ES256 相比 RS256 签名更短（64 字节 vs 256 字节）、签名更快，在没有 RSA 兼容性要求的新系统里是更好的默认选择——顺带也缓解了上面第 1 点的体积问题。

### 5. 必须校验 `iss` 和 `aud`

在多服务架构下，如果不校验 `aud`（受众），一个签发给"题库服务"的 token 可能被拿去调用"判题服务"或"管理后台"。RFC 8725 建议给不同用途的 JWT 使用不同的 `typ` 和必需 claim 集合，让一种 token 的校验规则天然拒绝另一种。

### 6. 客户端该把 token 存在哪

网页端不要无脑丢进 `localStorage`。同源页面里的任意恶意脚本都能读取 Web Storage，**一处 XSS 就能直接窃取 access token 和 refresh token。**

可选方案：

- 使用带 `HttpOnly`、`Secure`、合适 `SameSite` 属性的 Cookie 存储（同时必须补上 CSRF 防护：CSRF Token、Origin/Referer 校验）；
- 使用 BFF（Backend For Frontend）模式，把令牌完全保留在服务端，浏览器只持有一个会话 Cookie；
- access token 放内存（JS 变量），refresh token 放 HttpOnly Cookie，是一个常见的折中。

另外，防 XSS 不要指望一个通用的"可疑字符串过滤器"。可靠做法是在数据输出到 HTML、属性、JavaScript、CSS、URL 等不同上下文时分别做正确编码，必要时使用成熟的 HTML 净化库，再用 CSP 做纵深防御。

回到 OJ 这个系统，落地方案可以总结成一张表：

| 层次     | 手段                                                     | 解决的问题                                         |
| -------- | -------------------------------------------------------- | -------------------------------------------------- |
| 签名     | ES256 非对称签名，认证服务持私钥，各服务通过 JWKS 拿公钥 | 单服务被攻破不至于全线沦陷                         |
| 校验     | 硬编码算法，强制校验 `iss` / `aud` / `exp`               | `alg=none`、token 跨服务滥用                       |
| 生命周期 | access token 15~30 min + refresh token 数天并做轮换      | 续签；把作废的最坏延迟压到一个 access token 周期内 |
| 可控性   | Redis 存 `ver` + 按端分的 `sid`，各服务带本地缓存        | 改密 / 封号 / 权限变更 / 单端踢下线                |
| 业务约束 | 考试会话绑定 `sid` + `dev`，在答题接口校验               | 考试期间的答题入口互斥                             |

## 七、一点结论

写到这里，最初那个矛盾其实已经有了答案：

**JWT 最大的卖点是无状态，但在任何需要"立即撤销"的真实系统里，你都得把一部分状态加回来。** 差别只在于加回来的是一整份会话数据，还是一个几十字节的版本号。承认这一点，比强行捍卫"纯无状态"要务实得多。

所以：

- **不要为了用 JWT 而用 JWT。** 如果你的系统是个单体应用、用户量不大、也没有多端需求，`随机 Token + Redis` 简单可靠，没有任何问题——它甚至天然解决了本文一半的麻烦；
- **JWT 真正的价值在"多方验证"场景**：多个互不信任、不共享存储的服务需要独立校验同一份凭证。OJ 的去中心化鉴权正是这种场景，所以这个选型是成立的；
- **别把业务规则塞进身份凭证。** token 回答"你是谁"，业务服务回答"你现在能不能做这件事"。我们最初那个问题之所以让人困惑，就是因为它被下意识地当成了鉴权问题。

JWT 不是银弹。把它的边界看清楚，它就是个好工具。
